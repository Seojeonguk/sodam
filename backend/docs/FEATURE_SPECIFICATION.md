# Sodam 기능 명세서

## 문서 목적

이 문서는 현재 구현된 Sodam 서비스의 기능을 사용자 관점과 시스템 처리 관점에서 정리한 기능 명세서이다. API 호출 방식은 `API_SPECIFICATION.md`를 따르고, 이 문서는 기능 범위, 주요 흐름, 비즈니스 규칙, 예외 상황을 중심으로 설명한다.

## 서비스 개요

Sodam은 개인 또는 공유 가계부를 기준으로 수입과 지출을 기록하고, 카테고리별/기간별 소비 흐름을 확인할 수 있는 가계부 서비스이다.

주요 기능은 다음과 같다.

| 기능 영역 | 설명 |
| --- | --- |
| 회원 관리 | 회원가입, 로그인, 로그아웃, 토큰 재발급 |
| 세션 관리 | 액세스 토큰과 refresh token 기반 인증 유지 |
| 가계부 관리 | 사용자별 접근 가능한 가계부 조회, 생성, 수정, 삭제 |
| 거래 관리 | 거래 생성, 목록 조회, 상세 조회, 수정, 삭제 |
| 카테고리 관리 | 카테고리 생성, 목록 조회, 상세 조회, 수정, 삭제 |
| 분류 관리 | 가계부 기준 수입/지출 분류 조회 |
| 통계/대시보드 | 수입/지출 합계, 기간별 추이, 최근 거래, 주요 카테고리 확인 |

## 사용자 및 권한

### 사용자 유형

| 사용자 | 설명 |
| --- | --- |
| 비회원 | 로그인/회원가입 화면에 접근할 수 있는 사용자 |
| 회원 | JWT 인증 후 가계부, 거래, 카테고리, 통계 기능을 사용할 수 있는 사용자 |
| 가계부 소유자 | 가계부 생성 시 자동으로 부여되는 `OWNER` 권한 사용자 |

### 인증 상태별 접근

| 화면/기능 | 비회원 | 회원 |
| --- | --- | --- |
| 로그인 | 가능 | 가능 |
| 회원가입 | 가능 | 가능 |
| 대시보드 | 불가 | 가능 |
| 거래 내역 | 불가 | 가능 |
| 카테고리 관리 | 불가 | 가능 |
| 가계부 선택 | 불가 | 가능 |

프론트엔드는 보호 라우트 진입 시 메모리에 액세스 토큰이 없으면 refresh token으로 세션 복구를 시도한다. 복구에 실패하면 로그인 화면으로 이동한다.

## 회원 기능

### F-USER-001 회원가입

| 항목 | 내용 |
| --- | --- |
| 목적 | 사용자가 이메일, 비밀번호, 이름으로 계정을 생성한다. |
| 입력 | 이메일, 비밀번호, 이름 |
| 결과 | 사용자 계정 생성, 기본 가계부 생성, 기본 분류 생성 |
| 관련 API | `POST /api/auth/register` |

#### 처리 흐름

1. 사용자가 회원가입 정보를 입력한다.
2. 서버는 비밀번호를 암호화한다.
3. 이메일 중복 여부를 확인한다.
4. 신규 사용자를 `USER` 역할로 저장한다.
5. `account-book-service` 내부 API를 호출해 기본 가계부를 생성한다.
6. `category-service` 내부 API를 호출해 기본 분류 `INCOME`, `EXPENSE`를 생성한다.
7. 회원가입 성공 응답을 반환한다.

#### 비즈니스 규칙

| 규칙 | 설명 |
| --- | --- |
| 이메일 중복 불가 | 이미 사용 중인 이메일이면 회원가입을 실패 처리한다. |
| 기본 가계부 자동 생성 | 회원가입 완료 시 이름이 `가계부`인 기본 가계부를 생성한다. |
| 기본 분류 자동 생성 | 기본 가계부에 `INCOME`, `EXPENSE` 분류를 자동 생성한다. |
| 가계부 소유자 지정 | 기본 가계부 생성 시 가입 사용자를 `OWNER` 멤버로 등록한다. |

### F-USER-002 로그인

| 항목 | 내용 |
| --- | --- |
| 목적 | 사용자가 이메일과 비밀번호로 인증한다. |
| 입력 | 이메일, 비밀번호 |
| 결과 | 액세스 토큰 발급, refresh token 쿠키 저장 |
| 관련 API | `POST /api/auth/login` |

#### 처리 흐름

1. 사용자가 이메일과 비밀번호를 입력한다.
2. 서버는 이메일로 사용자를 조회한다.
3. 입력 비밀번호와 암호화된 비밀번호를 비교한다.
4. 인증 성공 시 access token과 refresh token을 생성한다.
5. refresh token은 `HttpOnly`, `Secure`, `SameSite=None` 쿠키로 응답에 추가한다.
6. access token은 응답 본문으로 반환한다.

#### 예외

| 상황 | 처리 |
| --- | --- |
| 이메일에 해당하는 사용자가 없음 | 사용자 없음 예외 |
| 비밀번호 불일치 | 로그인 실패 |

### F-USER-003 토큰 재발급 및 세션 복구

| 항목 | 내용 |
| --- | --- |
| 목적 | access token 만료 시 refresh token으로 새 access token을 발급한다. |
| 입력 | refresh token 쿠키 |
| 결과 | 새 access token 발급 |
| 관련 API | `POST /api/auth/reissue` |

#### 처리 흐름

1. 프론트엔드는 인증 API 호출 중 `401` 응답을 받으면 토큰 재발급을 시도한다.
2. 서버는 요청 쿠키에서 `refreshToken`을 찾는다.
3. refresh token 유효성을 검증한다.
4. token에서 사용자 이메일을 추출하고 사용자 존재 여부를 확인한다.
5. 새 access token을 발급한다.
6. 실패 시 프론트엔드는 access token을 제거하고 로그인 상태를 해제한다.

### F-USER-004 로그아웃

| 항목 | 내용 |
| --- | --- |
| 목적 | 사용자 세션을 종료한다. |
| 결과 | refresh token 쿠키 만료, 클라이언트 access token 제거 |
| 관련 API | `POST /api/auth/logout` |

## 거래 기능

### F-TX-001 거래 생성

| 항목 | 내용 |
| --- | --- |
| 목적 | 사용자가 수입 또는 지출 거래를 기록한다. |
| 입력 | 가계부, 분류, 카테고리, 금액, 설명, 거래일시, 만족도 |
| 결과 | 거래 데이터 저장 |
| 관련 API | `POST /api/transactions` |

#### 입력 규칙

| 필드 | 규칙 |
| --- | --- |
| `accountBookSeq` | 현재 선택된 가계부 ID를 사용한다. |
| `type` | `INCOME` 또는 `EXPENSE` |
| `amount` | 필수, 0보다 큰 값 |
| `categorySeq` | 필수 |
| `description` | 선택, 최대 255자 |
| `transactionDate` | 필수 |
| `satisfactionRating` | 선택, 1~5 |

#### 처리 흐름

1. 사용자가 거래 추가 모달을 연다.
2. 프론트엔드는 현재 가계부의 분류 목록과 카테고리 목록을 조회한다.
3. 사용자가 거래 정보를 입력한다.
4. 프론트엔드는 거래일시를 `YYYYMMDDHHmmss` 형식으로 전송한다.
5. 서버는 JWT 이메일로 사용자 ID를 조회해 `userSeq`를 설정한다.
6. 거래를 저장한다.
7. 프론트엔드는 거래 목록과 통계 데이터를 다시 조회한다.

| 색상 지정 | 색상 선택기를 통해 카테고리 색상을 지정한다. |

| 규칙 | 설명 |

### F-CAT-004 카테고리 삭제 및 거래 이동

| 항목 | 내용 |
| --- | --- |
| 목적 | 카테고리를 삭제하되 기존 거래가 참조하던 카테고리를 대체 카테고리로 이동한다. |
| 입력 | 삭제할 카테고리 ID, 대체 카테고리 ID |
| 결과 | 거래 카테고리 이동 후 카테고리 삭제 |
| 관련 API | `DELETE /api/categories/{id}`, `PUT /api/transactions/category/move` |

#### 처리 흐름

1. 사용자가 카테고리 삭제를 요청한다.
2. 프론트엔드는 삭제 대상 외 다른 카테고리 중 대체 카테고리를 선택하게 한다.
3. `category-service`는 `transaction-service`에 카테고리 이동을 요청한다.
4. `transaction-service`는 기존 카테고리 ID를 참조하는 거래를 새 카테고리 ID로 일괄 변경한다.
5. 카테고리 소유자를 검증한 뒤 카테고리를 삭제한다.

#### 비즈니스 규칙

| 규칙 | 설명 |
| --- | --- |
| 대체 카테고리 필요 | 삭제 시 `replaceCategoryId`가 필요하다. |
| 거래 무결성 유지 | 카테고리 삭제 전에 해당 카테고리를 참조하는 거래를 대체 카테고리로 이동한다. |
| 소유자만 삭제 가능 | 카테고리의 `userSeq`와 인증 사용자 ID가 같아야 한다. |

## 예외 및 제한 사항

| 항목 | 내용 |
| --- | --- |
| 한글 인코딩 | 일부 기존 소스/문서 주석 또는 화면 문자열은 인코딩이 깨진 상태로 보인다. 기능 자체는 코드 흐름 기준으로 정리했다. |
| 거래 상세/수정/삭제 권한 | 현재 코드상 일부 거래 단건 API는 인증 사용자 소유 여부 검증이 명시적으로 드러나지 않는다. |
| 가계부 수정/삭제 권한 | 현재 코드상 가계부 수정/삭제 시 멤버 권한 검증이 명시적으로 드러나지 않는다. |
| 분류 관리 | 공개 화면은 분류 조회 중심이며, 생성은 회원가입 내부 흐름에서 사용된다. |
| 카테고리 삭제 | 삭제 대상 외 대체 카테고리가 필요하므로, 카테고리가 1개뿐이면 삭제 흐름을 완료하기 어렵다. |
